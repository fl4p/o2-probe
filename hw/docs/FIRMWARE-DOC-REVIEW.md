# FINDINGS

1. [(b)] low - 1 - The 242/51-byte values and 98/462 counts are correct only as ideal maxima, not unconditional capacity - `firmware/FIRMWARE.md:85-94`; [RP002-1.0.5 §3.4.6](https://read.uberflip.com/i/1540208-rp002-1-0-5-lorawan-regional-parameters/36) gives DR5 `N=242` only without a repeater and with empty `FOpts` (`N=222` when repeater-compatible), while DR0 remains 51; [ChirpStack’s downlink table](https://github.com/chirpstack/chirpstack/blob/595aad4ef7d1b9981ac38e8a6d6887757a0d222a/lrwn/src/region/eu868.rs) confirms these are valid downlink limits, and `refs/tech/RS485-LS-SMT100.md:520` accurately states the DR0 value - the stated single-gateway topology makes the no-repeater assumption hold, but MAC commands, server caps, Dragino framing, and bootloader framing reduce usable image bytes - call them “best-case maximum application payload with no repeater and empty FOpts”; retain 98/462 only as PHY lower bounds.

2. [(c)] medium - 2 - The cited SF7 observation does not establish DR5 for application-update RX1 downlinks - `firmware/FIRMWARE.md:85-87` cites `refs/tech/chirpstack/README.md:345`, but `refs/tech/chirpstack/README.md:329-345` identifies it as an uplink join request; [RP002 §3.4.7](https://read.uberflip.com/i/1540208-rp002-1-0-5-lorawan-regional-parameters/36) makes RX1 DR depend on the immediately preceding uplink and `RX1DROffset`—with offset zero, only that same uplink’s DR is preserved - this leaves the 8.2-hour DR5 scenario unevidenced - cite an ordinary application uplink and verified offset, or label DR5 as a hypothetical best case.

3. [(c)] medium - 2 - RX2 is not an automatic retransmission “fallback whenever RX1 is missed” - `firmware/FIRMWARE.md:87`; [LoRaWAN 1.0.4 §§3.3.1, 3.3.5](https://read.uberflip.com/i/1428395-ts001-1-0-4-lorawan-l2-1-0-4-specification/11) says the server transmits in one of the two windows and the device opens RX2 only if it received no valid intended frame in RX1; an unconfirmed RX1 miss is unknowable to the server in time to repeat it in RX2 - this overstates failover behavior - say RX2 is an alternate scheduling window, defaulting to 869.525 MHz/DR0, not an automatic retry.

4. [(c)] medium - 4 - “3.6 h of gateway airtime” is the wrong quantity and not an unconditional regulatory floor - `firmware/FIRMWARE.md:96-100`; the correct transmitter time is `462×2.793472=1290.584 s=0.3585 h`, while `1290.584/0.10=3.58496 h` is elapsed time under uniform/per-packet 10% pacing; the [current EU SRD decision](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=OJ:L_202500105) confirms 869.4–869.65 MHz, 869.525 MHz within it, and ≤10% per transmitter over a continuous one-hour observation band - the gateway is the regulated transmitter, but burst-shaped compliance need not equal total airtime divided by 0.1 - write “about 3.585 h elapsed under continuous 10%-rate enforcement; actual TX airtime 0.3585 h.”

5. [(c)] medium - 5 - Class A proves one downlink per uplink, not “at most one per 300 s” - `firmware/FIRMWARE.md:83-84,109-111`; [LoRaWAN 1.0.4 §3.3](https://read.uberflip.com/i/1428395-ts001-1-0-4-lorawan-l2-1-0-4-specification/11) makes RX1/RX2 two windows of the same opportunity, while [§4.3.1.4](https://read.uberflip.com/i/1428395-ts001-1-0-4-lorawan-l2-1-0-4-specification/21) says `FPending` permits a Class A device to send another uplink as soon as possible - a server cannot send two downlinks for one uplink, but `FPending` can create another opportunity before TDC - qualify 300 s as conditional on the RS485-LS sending no intervening uplink.

6. [(c)] medium - 6 - `AT+CFGDEV` has a published LoRaWAN downlink equivalent, so “unverified” and “a channel that may not exist” are false - `firmware/FIRMWARE.md:81,102-107`; Dragino’s [RS485 Debug Command table](https://wiki.dragino.com/docs/LoRaWAN-End-Node/io-controllers-sensor-nodes/rs485-lb/#332-rs485-debug-command-atcfgdev) defines `A8 MM NN XX…YY`, including optional Modbus CRC and reply uplink, with a published 40-byte CFGDEV maximum; `refs/tech/dragino/DRAGINO.md:199` accurately says “most, not all” but cannot settle this command, and `refs/tech/RS485-LS-SMT100.md:254` is only one example rather than evidence for arbitrary frames - this materially changes the transport analysis and makes 98/462 only PHY minima - document the `A8` path and its 40-byte limit, then budget the real bootloader framing.

7. [(c)] medium - 6 - BLE can cross the RS-485 cable through `AT+CFGDEV`; it is not categorically “not a path to this MCU” - `firmware/FIRMWARE.md:102-104,115-120`; `refs/tech/dragino/DRAGINO.md:93-104,228-255` establishes that BLE is the AT console and `AT+CFGDEV` sends one raw RS-485 command, consistent with Dragino’s published command documentation; the wake citation at `refs/tech/dragino/DRAGINO.md:108` itself is accurate - BLE can therefore carry commands to an already-installed probe updater, although it cannot make an STM32G071 without self-programming code reflash itself - replace the categorical denial with that distinction.

8. [(c)] low - 6 - The BLE “measured truncation failure” is overstated - `firmware/FIRMWARE.md:122-125`; `refs/tech/dragino/DRAGINO.md:121` is only a heading, while `refs/tech/dragino/DRAGINO.md:131-134` explicitly says truncation was conjecture, observed once, and never isolated from the correlation with radio transmission - this turns uncertain evidence into an established failure mechanism - describe one unexplained rejection correlated with radio activity and retain the retry/read-back recommendation.

9. [(c)] low - 6 - `refs/tech/dragino/DRAGINO.md:350` supports OTA over BLE but not the asserted STM32L072 identity - `firmware/FIRMWARE.md:117-118`; the MCU appears only at `refs/tech/dragino/DRAGINO.md:355` for a measured D23-LB, not as a statement on line 350 about this RS485-LS - the operational conclusion that OTA updates the Dragino itself survives, but the citation is weaker than claimed - omit the MCU model or cite model-specific primary evidence.

10. [(c)] medium - 7 - The Debug Mate does not drive both blue `3V3` and `5V` pins as stated - `firmware/FIRMWARE.md:369-373`; the official [schematic, sheet 6](https://raw.githubusercontent.com/Seeed-Studio/OSHW-XIAO-Debug-Mate/51769f4dcb8829d95728eb34c37da2b4a58948bc/4_Hardware/Seeed_Studio_XIAO_Debug_Mate_V1.0_SCH_20250926.pdf) shows switched `VBUS_5V → XIAO_5V+`, whereas blue `3V3` is `X_3V3`, the plugged-in XIAO’s rail, and the [wiki](https://wiki.seeedstudio.com/getting_started_with_xiao_debug_mate/) says power measurement is through the 5V pin - leaving both disconnected remains prudent, but an empty socket’s `3V3` does not fight the probe LDO; correct the rationale accordingly. The Nucleo negative claim survives `refs/um3121.txt:449-517,563-603`, and the Debug Mate’s CMSIS-DAP VID/PID survives the official [source at lines 68–69](https://github.com/Seeed-Studio/OSHW-XIAO-Debug-Mate/blob/51769f4dcb8829d95728eb34c37da2b4a58948bc/0_Firmware/src/DapLink.cpp#L68-L69): `0x0D28/0x0204`.

# SURVIVED

1. Target 3 - The airtime arithmetic survives: 51 application bytes + 13 LoRaWAN bytes = 64 PHY bytes; SF12/BW125 gives 32.768 ms symbols, `DE=1`, CR 4/5, an 8-symbol preamble gives 12.25 transmitted preamble symbols, the payload formula gives 73 symbols, and total airtime is 2793.472 ms; 462 frames total 1290.584 s. Primary sources: [Semtech SX1276 datasheet](https://www.semtech.com/products/wireless-rf/lora-connect/sx1276) and [LoRaWAN 1.0.4 frame format](https://read.uberflip.com/i/1428395-ts001-1-0-4-lorawan-l2-1-0-4-specification/14). The stipulated `23,524/126,976=18.526%` also validates commit `3a3e2c9`’s 18.5% correction.

2. Cross-cutting conclusion - No finding overturns the release gate: LoRaWAN and BLE can carry bounded RS-485 commands, but neither can add missing self-programming code to the STM32G071; the RS-485 application bootloader/updater still must be installed and tested before potting. The corrected premise is “wireless may be a transport to an existing bootloader,” not “no wireless transport exists.”
